# mio 协议 v1 规范

本文是 mio 协议 v1 的候选规范，定义第三方实现互通所需的线上格式和行为。

本文沿用 [BCP 14](https://www.rfc-editor.org/info/bcp14)（RFC 2119 和 RFC 8174）的约束级别。
「必须」表示强制要求，「必须不」表示禁止，「应当」表示有充分理由才可偏离的建议，
「也许」表示实现可以自行决定是否采用。

## 协议版本

`v1` 表示协议主版本 1，对应 Go 参考实现中形如 `1.0.1` 的完整版本号。
版本号写作 `主版本.次版本.修订版本`，前缀 `v` 可用于显示。主版本是无前导零的正十进制数。
同一主版本的不同次版本和修订版本必须保持基础协议互通，例如 `v1.0.1` 和 `v1.0.10000`。

自 v1 起，下文指定的密钥派生位置必须使用 `KDF_VERSION`。其值由主版本的十进制 ASCII 字符串
拼接 ASCII `.0.0` 得到。主版本 1 的标签固定为 `1.0.0`（十六进制 `31 2e 30 2e 30`），
主版本 2 的标签为 `2.0.0`。标签不带 `v` 前缀、终止符、空格或换行。

v1 没有线上协议版本字段或版本协商。客户端和服务端须事先配置为兼容的协议版本。
密钥派生标签不匹配时，TCP 认证记录或 QUIC 初始标记的校验会失败，服务端按对应路径的认证失败规则处理。
接收方无法仅凭认证失败确定是密钥、版本还是其他认证输入不匹配。
mio `v0.6.2` 使用派生标签 `0.6.2`，因此无法与采用 v1 的对端通过认证。

凡是会使遵循同一规范的对端无法完成认证、解析线上消息或继续会话的变更，必须提高协议主版本号。
不同主版本使用不同的密钥派生标签，因此不能相互认证。v1 接收方可跳过未知帧，因此新增帧只有在对端
跳过后仍能正确运行时，才可以作为兼容扩展。程序发布版本可以独立更新。

## 总览

mio 有两条传输路径。启用两条路径时，服务端在同一个端口号上分别监听 TCP 和 UDP：

- **TCP 路径**：外观是一条到伪装站（`dest`）的普通 TLS 连接，认证后数据由 mio 自己的记录层加密。一条连接上可以同时承载多个代理连接，就像浏览器在一条 HTTP/2 连接上发出多个请求。
- **QUIC 路径**：使用 QUIC v1 和 TLS 1.3，ALPN 为 `h3`。ClientHello.random 携带标记，握手后交换 mio 双向证明，代理数据由 QUIC 保护。

两条路径在认证之后使用相同的[目标请求](#目标请求)格式。实现也许仅启用 TCP 路径，也许支持
[UDP 转发扩展](#udp-转发扩展)。

## 密钥

服务端持有一对 X25519 静态密钥，由 `mio keygen` 生成：

- **私钥** `S`：只放在服务端（`[inbounds].private_key`）。
- **公钥** `S_pub`：配置在获授权的客户端（`[outbounds].public_key`）。客户端用它验证服务端身份，对服务端而言，持有该值即可构造有效的客户端认证。部署者必须按访问凭据保护此值。

配置中的两把密钥都编码为不带填充的 URL 安全 base64（43 个字符）。在线上格式和密码计算中使用解码后的
32 字节原始值。实现必须不接受全零的 X25519 共享结果。

`‖` 表示字节拼接。整数均为无符号，多字节整数用大端编码。格式中的双引号字符串按 ASCII 字节编码。
`HKDF` 指 [RFC 5869](https://www.rfc-editor.org/rfc/rfc5869.html) 的 HKDF-SHA256，执行 Extract 和 Expand 两步。
空 salt 或空上下文用空字节串表示。`AEAD` 指 AES-256-GCM，使用 12 字节 nonce 和 16 字节 tag。记录体中的 tag 紧跟密文。

## TCP 路径

### 借用伪装站完成 TLS 握手

1. 客户端必须向服务端发起 TLS 握手，将 SNI 设为 `dest`，并在首个 ClientHello 中提供 X25519（group `0x001d`）的 `key_share`，保留与它配对的私钥供 mio 认证使用。客户端也许模仿 Chrome 的 ClientHello 指纹。Go 参考实现使用 uTLS。
2. 服务端为每个入站连接拨号 `dest:dest_port`，按 TLS 记录双向原样转发，同时记下：
   - `client_random`：首个 ClientHello 的 random（32 字节）。
   - `E_pub`：ClientHello 里 `key_share` 扩展中 X25519（group `0x001d`）的份额（32 字节）。
   - `server_random`：最后一条 ServerHello 的 random（出现 HelloRetryRequest 时以最后一条为准）。
3. 客户端必须与真实的伪装站完成 TLS 1.3 握手，并按 TLS 规则校验其证书。为与参考服务端互通，
   客户端必须在一条 TLS 握手记录中发送完整的首个 ClientHello。

### 认证记录

客户端在发出 ClientHello 之前就持有 `E_pub` 对应的私钥 `E`，两端可以算出同一个共享密钥：

```
shared = X25519(E, S_pub) = X25519(S, E_pub)
```

`E_pub` 本来就是 ClientHello 里的普通 key_share，所以这一步不会在线上多出任何字节。

握手完成后，客户端直接在 TCP 上连续发出两条记录，**认证记录**和**份额记录**：

```
key    = HKDF(ikm = shared, salt = client_random ‖ server_random, info = "mio auth " ‖ KDF_VERSION, 32)
header = 17 03 03 ‖ length(2)            ; length = len(plaintext) + 16
record = header ‖ AEAD-Seal(key, nonce, plaintext, ad = header)

认证记录：nonce = 0^12，     plaintext = random_padding(71)
份额记录：nonce = 0^11 ‖ 01，plaintext = client_share(1216) ‖ random_padding(0–255)
```

- `client_share` = X25519 公钥（32）‖ ML-KEM-768 封装公钥（1184）。
- 认证记录的明文只有随机填充，它的作用是证明发送方算得出 `key`。记录体因此固定是 87 字节，
  与 Chrome 在 HTTP/2 连接开头发出的第一条记录（连接前言、SETTINGS 和 WINDOW_UPDATE）一样长（Chromium 157 实测）；紧随其后的份额记录则处在浏览器第一个请求的位置上。

服务端取得 ServerHello 的 random 和首个 ClientHello 的 X25519 份额后，用 `S` 和 `E_pub` 算出 `shared`。
服务端必须检查随后来自客户端的前 8 条 Application Data 记录，直到认证成功。外层类型为 Application Data
的 TLS 1.3 加密握手记录也计入这 8 条。能用认证 nonce 解密且明文长度不超过 256 字节即为认证通过。
出现 HelloRetryRequest 时，`E_pub` 仍取首个 ClientHello 的份额。

认证未通过的记录必须原样转发给伪装站。若缺少所需的握手参数，或检查完 8 条记录仍未通过，
服务端继续原样转发且停止尝试认证。认证通过后，服务端必须消费认证记录，停止转发并关闭到
`dest` 的连接。下一条记录必须是能用份额 nonce 解密的 Application Data 记录，明文不得短于
1216 字节。服务端只取前 1216 字节作为 `client_share`。等待份额的时限为 5 秒，超时、记录无效或份额无效时
服务端必须关闭连接。

因为密钥依赖每条连接都不同的 `server_random`，所以录下的认证记录无法在别的连接上重放。
不知道 `S_pub` 的人算不出 `shared`，造不出认证记录；被动监听者也无从离线猜测，因为没有任何低熵的秘密。

### 密钥交换与会话密钥

两个方向的密钥由下面的函数派生（代码中为 `protocol.DeriveKeys`）：

```
DeriveKeys(secret):
  ikm  = secret ‖ shared
  salt = client_random ‖ server_random
  c2s  = HKDF(ikm, salt, "mio c2s", 32)      ; 客户端 → 服务端
  s2c  = HKDF(ikm, salt, "mio s2c", 32)      ; 服务端 → 客户端
```

1. 客户端份额使用新生成的 X25519 临时密钥和 [FIPS 203](https://csrc.nist.gov/pubs/fips/203/final)
   定义的 ML-KEM-768 封装公钥。服务端从份额记录里取出 `client_share`，生成自己的 X25519 临时密钥，
   对客户端的 ML-KEM-768 公钥做封装，得到：
   - `server_share` = X25519 公钥（32）‖ ML-KEM-768 密文（1088）
   - `secret` = X25519 共享密钥（32）‖ ML-KEM 共享密钥（32）
2. 服务端用 `DeriveKeys(空)` 的 `s2c` 密钥，以序号 0 发出一条 **ready 帧**（流编号为 0），负载为 `server_share`。
3. 客户端等待 ready 时，必须跳过记录头和长度有效但在预备密钥下认证失败的记录，且跳过时序号保持 0。
   参考客户端在发送完份额记录后最多等待 3 秒。首条通过 AEAD 认证的记录必须是 ready 帧，
   负载长度为 1120 字节。遇到格式错误、错误帧类型、无效份额或超时，客户端必须结束握手。
4. 服务端发完 ready，客户端验证并处理 ready 后，双方必须切换到 `DeriveKeys(secret)`，
   两个方向的序号独立重置为 0。此后所有记录都使用会话密钥。

### 记录层与帧

每个帧单独封装成一条 TLS Application Data 记录：

```
header = 17 03 03 ‖ length(2)       ; length = len(frame) + 16
record = header ‖ AEAD-Seal(key, nonce(seq), frame, ad = header)
nonce(seq) = 0^4 ‖ seq(8)          ; seq 每个方向独立，从 0 开始，每条记录加 1
```

发送方必须不写出超过 16401 字节的记录体（密文），该上限对应不带填充的 TLS 1.3 记录（16384 字节明文 + 1 字节类型 + 16 字节 tag）。
接收方必须支持最长 16640 字节的记录体。解密后的帧为：

```
frame = type(1) ‖ stream_id(4) ‖ payload_length(2) ‖ payload ‖ padding
```

| type | 名称   | 含义                                                                               |
| ---- | ------ | ---------------------------------------------------------------------------------- |
| 0    | ready  | 服务端就绪，负载为 `server_share`，`stream_id` 为 0                                |
| 1    | data   | 流上的应用数据，负载最长 16378 字节                                                |
| 2    | close  | 发送方不再在这条流上发送数据（半关闭），负载为空                                   |
| 3    | reset  | 发送方放弃这条流，不再读也不再写，负载为空                                         |
| 4    | window | 流量控制，负载为 4 字节正整数。流编号为 0 时更新会话窗口，其余编号更新对应的流窗口 |

- 接收方必须按 `payload_length` 取负载并丢弃剩余的填充字节。填充字节可为零。
- 认证后的会话中，接收方遇到无效记录头、截断记录、AEAD 认证失败、短于 7 字节的帧头、
  或 `payload_length` 超过剩余明文长度时，必须关闭整个会话。
- 接收方必须跳过结构有效但 `type` 未知的帧。跳过的记录仍消耗当前方向的记录序号。

### 密钥使用上限

会话密钥建立后，两个方向分别计数。发送方在每个方向的同一密钥下最多加密
`2^24`（16,777,216）条记录，计入所有帧类型，包括控制帧和带填充的帧。发送方必须不在同一密钥下重用
nonce 或让序号回绕。序号从 0 开始，因此发送方必须在尝试加密序号为 `2^24` 的记录之前关闭
整个 TCP 会话。接收方必须在尝试解密超出该上限的记录之前关闭会话。

本版本无会话内 KeyUpdate。会话关闭后，已有流随之结束。客户端也许重新握手建立具有新密钥的会话，
供后续代理连接使用。该上限参考了 [RFC 9846 §5.5](https://www.rfc-editor.org/rfc/rfc9846.html#section-5.5)
对 TLS 1.3 AES-GCM 满长记录的用量限制，采用较低的 `2^24`。

### 流

握手完成后，一条连接上可以同时有多条**流**，每条流承载一个代理连接，并各自进行流量控制。

- **打开**：只有客户端可以打开流。客户端必须从 1 开始分配 `stream_id`，每条新流加 1，
  并按编号递增的顺序发送各流的第一个 data 帧。服务端收到编号大于已见最大值的 data 帧时，
  将它视为打开新流。编号 0 保留给会话级控制帧。
- **半关闭**：一方发完数据后发 close 帧。发送方必须不在该流的同一方向再发送 data 帧。
  接收方读完 close 前收到的数据后读到结束，反方向仍可继续发送。两个方向都结束后，该流可以释放。
- **放弃**：一方不想再读写时发 reset 帧。对端收到后，这条流上的发送立即失败。reset 前收到的数据仍可读完，
  之后的读取得到结束（对端已先发过 close 帧）或错误。
  在还没读到对端 close 帧时关闭一条流，应当先发 close 帧（如果自己还没发过），再发 reset 帧。
- **关闭后收到数据**：收到某条流的 close 或 reset 帧后，接收方必须丢弃对端随后发给该流的 data 帧。
  这些帧计入会话窗口并在丢弃后归还会话额度，无需扣减或增加流窗口。会话窗口溢出仍按会话错误处理。
- **已结束的流**：收到属于已结束流的帧、或属于未知流的非 data 帧时，直接丢弃。编号 0 的 window 帧按会话处理。
- **并发上限**：每条 TCP 会话同时最多承载 100 条流。服务端用 reset 帧拒绝超过上限的新流。
- **流量控制**：每个方向都有 32 MiB 的会话窗口，每条流另有 16 MiB 的流窗口。发送 data 帧时按负载字节数同时扣减两个窗口，任一窗口耗尽后等待对应的 window 帧。接收方在应用读走数据后归还会话额度和仍在接收数据的流额度。被丢弃的 data 也占用会话额度，丢弃后归还。控制帧和填充不占用额度。
  收到超出会话窗口或仍在接收数据的流窗口的 data 帧、负载长度不等于 4 字节的 window 帧，
  或会使适用窗口超出初始值的增量时，
  接收方必须关闭整个会话。编号为 0 或指向现存流的 window 帧增量为零时，也必须关闭会话。
- **连接关闭**：TCP 连接断开或出现协议错误时，其上所有的流一并失效。

客户端的行为（不影响互通）：所有代理连接尽量复用同一条 TCP 连接；一条连接上的流达到 100 条时再开一条；
连接上没有任何流的状态持续 4 到 6 分钟（随机）后关闭它。

### 填充

参考实现采用以下填充策略。发送方也许采用其他长度策略，但仍须遵守记录长度上限。

- ready 帧：0–1024 字节。
- 每条流在每个方向上的前 8 个 data 帧：负载不足 900 字节的，补到整帧 900–1400 字节；其余随机加 0–255 字节。
- 之后的 data 帧，以及 close、reset、window 帧不填充。
- 例外：目标请求和应答所在的 data 帧，填充 16–512 字节。

大块数据按一帧 16378 字节的负载发出，正好填满一条最大的记录，记录长度与被代理连接自身的分包方式无关。

## QUIC 路径

### 标记

客户端把 ClientHello.random 设为：

```
nonce  = 随机 16 字节
minute = floor(unix_time / 60)，8 字节
marker_key = HKDF(ikm = S_pub, salt = 空, info = "mio quic marker " ‖ KDF_VERSION, 32)
random     = nonce ‖ HMAC-SHA256(marker_key, nonce ‖ minute)[:16]
```

客户端必须在 QUIC v1（版本字段 `0x00000001`）的 Initial 中携带此标记。为与参考服务端互通，
首个 Initial 必须位于其 UDP 数据报开头，且该 Initial 的 CRYPTO 数据必须包含从偏移 0 起的至少 38 个连续字节，
即 TLS 握手消息头、ClientHello 的 `legacy_version` 和完整 random。

服务端按 [RFC 9001 §5.2](https://www.rfc-editor.org/rfc/rfc9001.html#section-5.2) 处理 Initial，取出 random，
并以本地当前分钟及其前后各一分钟重算标签。服务端必须拒绝重复使用的 nonce，并把接受的 nonce 至少保留 5 分钟。
无有效标记、含重复 nonce 或不能识别为 mio Initial 的新流量进入伪装站的 UDP 回落路径。

### 握手与认证

QUIC 路径必须使用 TLS 1.3，ALPN 必须为 `h3`。客户端把 SNI 设为 `dest`。
参考服务端使用临时自签证书。客户端也许接受自签证书，但必须校验下面的 mio 服务端证明。

```
exporter = TLS-Exporter("mio quic auth", 空, 32)          ; 双方各自导出，绑定到这条 QUIC 连接
C        = 客户端新生成的 X25519 临时密钥
shared   = X25519(C, S_pub) = X25519(S, C_pub)
key      = HKDF(ikm = shared, salt = exporter, info = "mio quic auth " ‖ KDF_VERSION, 32)
```

1. TLS 握手完成后，客户端必须在自己发起的第一个双向流（QUIC 流编号 0）上发送
   `C_pub(32) ‖ HMAC-SHA256(key, "client")`，共 64 字节。该流专用于认证。
2. 服务端算出 `key` 并校验客户端证明，通过后回复 `HMAC-SHA256(key, "server")`（32 字节），
   然后结束认证流的发送方向。
3. 客户端必须在验证服务端证明后才能发送代理请求。证明无效、认证消息无法读取或认证超时时，
   检测到失败的一端必须关闭 QUIC 连接。已经通过标记分流的连接在此阶段失败时，不再向伪装站回落。
   参考实现采用 5 秒认证超时，服务端分别限制等待认证流和在该流上读写的时间。

只有持有 `S` 的一方能算出服务端的回复，所以即使客户端不校验证书，中间人也无法冒充服务端。

### 数据

客户端每发起一个代理连接必须打开一个新的双向 stream，先交换[目标请求](#目标请求)，再直接传输原始字节。
一方结束发送时使用 QUIC 流的 FIN，反方向仍可继续传输。放弃单条代理流可以使用 QUIC 的流取消机制。

QUIC 路径遵循 [RFC 9000](https://www.rfc-editor.org/rfc/rfc9000.html) 的包填充要求。
实现也许会使用 [QUIC PADDING 帧](https://www.rfc-editor.org/rfc/rfc9000.html#section-19.1) 额外填充包。
本版本未规定用于掩蔽目标请求、应答或数据长度的额外包级填充策略。实现必须不在认证流或代理流中插入填充字节。

### 网络地址变化

v1 客户端必须以服务端观察到的源 IP 和 UDP 源端口在会话期间保持稳定为前提。主动换网时，
客户端必须新建 QUIC 连接并重新认证。如果换网或 NAT 重新绑定导致旧连接失效，客户端也许会通过
新的 QUIC 会话或 TCP 路径承载后续请求。已有代理流不能迁移或续传到新的 mio 会话。
参考服务端按源 IP 和端口分流，无法把来自新地址的旧连接数据报归入原会话。

### 客户端选路

客户端也许会根据连接结果或延迟为后续连接选路，也许会并发尝试两条路径。这两项行为均可独立采用。
切换首选路径时，已有流继续使用各自打开时的会话。参考实现以 TCP 为初始首选路径，
按需要尝试备用路径，并定期重新比较两条路径。

## 目标请求

每条代理流（QUIC 路径上是每个代理 stream）由客户端发送目标请求。请求的第一个字节区分 TCP
目标地址、UDP 关联和提前发送 TCP 数据的能力探测。

```
request = atyp(1) ‖ address ‖ port(2)
  atyp 1：address = IPv4（4 字节）
  atyp 3：address = length(1) ‖ 域名（1–255 字节）
  atyp 4：address = IPv6（16 字节）
```

服务端必须对格式有效的请求尝试建立到目标的 TCP 连接，并回复 1 字节。成功时回复 `0`，
随后双向转发数据。连接失败时回复 `1` 并结束此流。未确认支持[提前发送 TCP 数据](#提前发送-tcp-数据)时，
客户端必须在收到成功应答后才发送应用数据。
任何非零应答都表示失败。收到未知地址类型、零长度域名或未读完整请求就遇到流结束时，
服务端必须结束这条流。
在 TCP 路径上，实现必须将请求和应答各自放在一个 data 帧里。在 QUIC 路径上，实现必须直接将它们写在 stream 上。

### 提前发送 TCP 数据

客户端也许在已认证会话上开一条独立的代理流，发送单字节 `02` 探测此能力。支持的服务端必须回复
单字节 `00` 并结束该流。探测不建立目标连接。旧服务端会把 `02` 视为未知地址类型并结束该流。
探测失败或超时后，客户端仍可在同一会话中使用普通目标请求。

收到成功的探测应答后，客户端也许在同一会话中发送 TCP 目标请求，并在收到目标应答前发送应用数据。
服务端必须按流内顺序处理这些字节，只在成功连接目标后才向目标转发，并在向客户端转发目标数据前发出成功应答。
目标连接失败时，服务端必须丢弃此流的应用数据。客户端一旦向某条路径发送了应用数据，必须不因等待目标应答失败
而自动把这些字节重发到另一条路径。

## UDP 转发扩展

客户端在新代理流上发送单字节 `00` 来建立一个 UDP 关联。服务端支持该扩展时，回复单字节
`00` 表示关联已就绪。拒绝时也许返回非零应答后结束流。旧服务端会把 `00` 当作未知地址类型并结束流。
客户端必须收到 `00` 应答才可发送数据报。拒绝或无应答时只结束该关联。TCP 目标请求的格式保持不变。

一个关联可以访问多个目标。双方在流上依次写出带长度的数据报。

```
datagram = length(2) ‖ atyp(1) ‖ address ‖ port(2) ‖ payload
```

`length` 是其后地址和负载的总字节数，范围是 5 至 65504。地址编码与 TCP 目标请求相同。
客户端发送的是目标地址和端口，服务端回复的是实际来源的 IP 地址和端口。每条消息对应一个 UDP 数据报，
允许空负载。实现必须保留数据报边界，允许消息跨多个 TCP data 帧或 QUIC STREAM 帧。
实际可用的最大负载还取决于地址字段长度及底层 UDP 路径限制。

显式代理可以发送域名，由服务端解析。此时服务端回包仍报告实际来源的 IP 和端口，一个 IP 可能对应多个域名，
因此客户端无法仅凭回包地址推断原域名。

透明代理若需要保持应用看到的 UDP 对端地址，必须为对应的流选择并固定真实目标 IP，再以 IP 地址发送到 mio。
对于 Fake-IP，客户端先找回原域名并解析真实 IP，同时保留应用原来使用的地址和端口。收到来自选定对端的回包后，
透明代理必须在向应用交付前恢复原来的来源地址。应用直接访问真实 IP 时，保留该 IP 和端口。

收到非法长度或流在消息中途结束时必须终止关联。地址格式非法或目标无法转发时，接收方丢弃该条数据报，
仍可继续处理同一关联的其他数据报。任一方向关闭代理流即结束关联，服务端释放对应的 UDP 套接字。
参考服务端对每个关联最多保留 64 个目标套接字，空闲约 60 秒后回收。超过上限时，新目标的数据报会被丢弃。

参考客户端设为 `[outbounds].socks5_udp = true` 时，通过
[SOCKS5 UDP ASSOCIATE](https://www.rfc-editor.org/rfc/rfc1928.html#section-7) 提供该功能。
关闭 SOCKS5 的 TCP 控制连接会结束关联。参考客户端仅接受来自控制连接对端 IP 的数据报，
按请求提供的端口或首条有效数据报的源端口绑定，并丢弃 SOCKS5 分片（`FRAG` 非零）。

UDP 负载在 mio 两端之间走可靠、有序的代理流，同一条流上的后续数据报可能等待丢失的数据重传。
流外的 UDP 仍可能丢包或乱序。

## 在其他 Go 项目中使用参考实现

如果您开发一款通用代理内核希望引入mio协议，mio提供导出函数以供您方便的引入。

```go
import "github.com/orgmio/mio/protocol"
```

| 接口                                                          | 作用                                                  |
| ------------------------------------------------------------- | ----------------------------------------------------- |
| `DialSession(ctx, Peer)` / `Session.Dial(ctx, target)`        | 客户端 TCP 路径：建立一条连接，在其上打开多个代理连接 |
| `Handshake(ctx, conn, Peer)`                                  | 只做客户端握手，返回 `*Session`                       |
| `VerifyAuth` / `Accept`                                       | 服务端认证与握手，`Accept` 返回 `*Session`            |
| `GenerateKeyPair` / `ParsePrivateKey` / `ParsePublicKey`      | 密钥生成与解析                                        |
| `Session`                                                     | 记录层与流（`Open` / `Accept`）                       |
| `DeriveKeys`                                                  | 密钥派生                                              |
| `WriteRequest` / `ReadRequest` / `WriteReply` / `ReadReply`   | 请求格式                                              |
| `StreamRequest` / `ReadStreamRequest` / `Session.DialRequest` | 打开 TCP 请求或 UDP 关联                              |
| `WriteDatagram` / `ReadDatagram` / `ParseDatagram`            | UDP 关联的数据报格式                                  |
| `client.Dialer.ListenUDP`                                     | 为透明代理提供以 IP 地址收发数据报的 UDP 关联         |
| `protocol/quicauth`                                           | 标记、重放缓存与认证（`ClientAuth` / `ServerAuth`）   |
| `Version`                                                     | Go 参考实现报告的协议版本                             |

`protocol` 及其子包不依赖 quic-go。只有引用 `client`、`server` 包时才需要 quic-go，而且这时需要在自己的 `go.mod` 里加上与 mio 相同的 `replace`：

因为mio为了加速UDP部分，引入了已经成熟的由hysteria社区维护的quic-go。
但hysteria社区将他们的github组织名改了，而包名没改，所以这里做一个重定向。

```text
replace github.com/apernet/quic-go => github.com/HyNetworks/quic-go
```
